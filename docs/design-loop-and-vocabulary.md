# Design loop and plan vocabulary — work packages

Date: 2026-09-18. Status: proposed, awaiting the user's go. Author: claude (bot).
Scope: items 1 and 2 of the September 18 shortlist. Everything else waits until these ship.

Authority order follows `docs/praya/README.md`. Nothing here authorizes live-world writes; the placement milestone stays paused.

## Why these two first

On September 18 a bot designed a six-storey tower on the Praya first plot through the studio contract in about two hours of wall-clock time. Two of the three failed attempts were not design failures: one was a survey height cap the agent could not see, the other was a stair geometry bug the walk model reported as "door unreachable" with no location. Every render, floor cut and critique was scripted by hand outside the repo, and the agent had to write its own pane-state resolver because the compiler will not. Package A makes that loop a product feature; package B removes the hand-rolled parts of the plan language. Both are prerequisites for a fair multi-model bake-off with recorded provenance.

## Package A — the design loop

**Outcome.** An agent (or a person) posts a plan and gets back, in one response, everything needed to judge it and fix it: compiled candidate, rule diagnostics with cell locations, a walking report that says *where* the route breaks, and a review sheet of images. A second agent, or the same one later, can reproduce the exact same judgement from the saved record.

### A1. Diagnostics with locations and rule IDs

Replace the flat `diagnostics: [...]` array with entries of the shape

```json
{"rule":"walk.door-unreachable","severity":"error","component":"flat-doors-0","at":[10,6,8],
 "message":"No supported two-block-high route from the street frontage","hint":"Nearest reached cell [11,6,8]; blocked at [13,5,10] by minecraft:polished_deepslate (tower-slab-1)"}
```

Rules, all pure geometry over the compiled candidate plus survey, each with a stable ID and version:

| Rule | Severity | What it checks |
|---|---|---|
| `bounds.survey-cap` | error | any owned cell above the survey top; report the cap (the bug that cost R0 its eleven storeys) |
| `walk.door-unreachable` | error | existing check, now with the last reached cell and the first blocking cell |
| `walk.headroom` | warning | any reached cell whose two-high column is blocked by a non-air, non-door, non-carpet block |
| `support.floating` | warning | non-air cell with air on all six faces, excluding leaves, panes, bars, lanterns, signs |
| `roof.uncovered` | warning | an interior floor cell with no non-air block anywhere above it inside the plan bounds |
| `light.dark-corridor` | info | reached cell farther than 8 blocks from any light-emitting block |
| `sign.orphan` | error | sign text whose cell is not a wall sign, or a wall sign without a supporting block behind it |
| `pane.unresolved` | warning | pane or bar state whose connection flags disagree with its neighbours (goes away once B2 lands) |

Implementation: one module `preview/diagnostics.cjs` exporting `diagnose(candidate, site, transform) -> entries`. `accessibility.cjs` folds in as the `walk.*` family. `design-service.evaluate` calls it once per compile. Diagnostics are stored on the draft and copied to the saved revision so a later reviewer sees what the author saw.

### A2. Review sheet: rendered on save and on request

A server-side renderer produces PNGs from a candidate hash without a browser session:

- Six exterior views (perspective, front, side, rear, roof, street) using the same presets the studio uses.
- One plan cut per occupied floor, top-down orthographic, with a label strip: level name, component legend, and the diagnostics of that level drawn as coloured cell markers.
- Four true elevations (orthographic, one per compass face), which the studio does not currently have.

Route: `GET /api/workspace/artifacts/{hash}/sheet/{view}.png` plus `sheet/index.json` listing what exists. Files are content-addressed under `.workspace/sheets/{hash}/` and generated by a bounded worker (one at a time, 60 s cap, reuse `thumbnail-render.js` and the headless Chromium already used by `generate-thumbnails.cjs`). Rendering is triggered on save and lazily on first request for any draft; the studio shows the sheet in a "Review" tab under the model.

The context endpoint returns the sheet URLs, so an agent can fetch images without driving a browser. This is the "eyes" the design loop needs.

### A3. The round-trip contract for agents

`drafts/{id}/context` grows to include: `diagnostics` (A1 shape), `sheet` (A2 URLs), `site.caps` (top of survey, plot bounds, frontage, protected volumes in plan coordinates), `author`, and `limits`. `drafts` POST already takes `author`; `drafts/{id}/edit` starts accepting it too, so the model that revised a plan is the one recorded.

A CLI verb `node preview/workspace-cli.cjs review <draft-id>` prints the diagnostics and downloads the sheet to a folder. That is the whole loop for any bot: post, review, edit, review, save.

### A4. Bake-off runner

`node preview/bakeoff.cjs brief.json` takes a brief (site, transform, text, optional reference images) and a list of entrants (`{agent, model, effort, command}`), runs each entrant's command with the brief on stdin, expects a plan on stdout, posts it with the right `author`, and writes a comparison record: one row per entrant with cells, components, diagnostics counts, walk result, sheet links. The runner never judges; the user does, blind if they want (entrants get letters in the sheet until revealed). The record is saved under `.workspace/bakeoffs/` and shown in the Design library.

### Acceptance

- Re-post the September 18 R0 attempts unchanged: attempt one fails on `bounds.survey-cap` with the cap number; attempt two fails on `walk.door-unreachable` naming `[13,5,10]` as the blocker. Both currently fail with less.
- Every saved version in the register has a sheet; the seventeen catalogue artifacts render byte-identical geometry to today.
- A bot with no browser can run post → review → edit → save using only the CLI, and the saved record shows its model and effort.
- Pytest wrappers: rule fixtures for each row in the table, sheet index contract, bake-off record schema.

Estimate: three to four bot sessions. A1 and A3 first (one session), A2 second, A4 last.

## Package B — plan vocabulary

**Outcome.** A plan says what a building is made of, not which 4,000 cells to fill. The compiler owns the tedious, error-prone geometry: repeats inside repeats, pane and bar connection states, and a library of parameterized parts that any plan can call.

### B1. Schema version 2 of the plan

Additive. Version 1 keeps compiling forever; the seventeen catalogue artifacts are the regression fixture.

- `repeat` may nest, to depth 3, with the existing 4,096-primitive and 100,000-work budgets enforced on the expanded result.
- New `op: "fill"`: box with `material` for the shell and `interior` for the inside, so a room is one op instead of six.
- New `op: "call"`: invoke a library part with parameters, e.g. `{"op":"call","part":"stair.switchback","at":[11,5,9],"params":{"rise":4,"width":2,"facing":"south"}}`. Cells the part emits are owned by the calling component, so revision semantics and overlap checks are unchanged.
- `palette` values may name a block *without* connection properties for panes, bars, walls, fences and glass; the compiler resolves them (B2).
- `signs` may attach to a `call` that emits a sign so the part positions it.

### B2. Connection-state resolution in the compiler

Port `preview/thin-block-connections.cjs` (`resolveConnections`) to Java inside `PlanCompiler`, run after ownership is settled and before hashing. Rules: panes and bars connect to full blocks, other panes and bars, and walls; walls connect similarly and gain `up`; fences connect to fences and full blocks; stairs get `shape` from neighbouring stairs. Applies only to palette entries that omit the properties, so authored states stay authoritative. The September 18 generator's resolver becomes dead code and is deleted.

### B3. Part library

Parts live in `src/main/resources/parts/*.json` (shipped with the compiler) and `preview/.workspace/parts/` (workspace-local, for experiments). A part is a plan fragment with declared parameters, defaults and bounds, plus a required `test` block: at least one instantiation that must compile and pass the A1 rules. First set, taken from what the catalogue and the tower actually needed:

`stair.straight`, `stair.switchback`, `core.lift`, `facade.pier-bay` (pier, recessed pane, rail), `facade.punched-window` (with optional trapdoor shade), `balcony.planted`, `roof.parapet`, `roof.screen`, `entrance.canopy`, `sign.wall-framed` (the dash-rule sign the user asked for), `kitchen.run`, `bed.alcove`, `seat.pair`.

Parts carry `provenance` (who authored, which project it was lifted from) and a `style` tag so B4-style rules can later say "Old Town uses `facade.punched-window` not `facade.pier-bay`". The studio lists parts in the Adjust panel; choosing one inserts a `call` at the selected cell.

### B4. Retire the legacy per-block path

`/pbuilder generate` (Gemini → BlockGrid) stays for one release with a startup warning, then goes. `BlockGrid` remains as the schematic reader. The README stops describing per-block JSON as a way to build.

### Acceptance

- Every v1 catalogue plan compiles to the same hash under the v2 compiler.
- The Point Tower R1 plan re-authored in v2 is under 400 lines (today 2,060 ops) and produces the same candidate hash once B2 resolves the panes.
- Each library part has a passing test instantiation and an entry in a generated `docs/parts.md`.
- Java probes plus pytest wrappers for nesting depth, budgets on expanded output, `call` parameter bounds, and resolution parity with `thin-block-connections.cjs`.

Estimate: three sessions. B2 first (smallest, unblocks the tower cleanup), then B1, then B3, with B4 as a one-line change at the end.

## Order and decisions needed

1. A1 + A3, then B2. Both are small and remove the two things that wasted the most time on September 18.
2. A2 (sheets), then B1.
3. B3 (parts), then A4 (bake-off runner), which needs parts to be fair across models.

Decisions for the user:

- **Sheet size and count.** Six exteriors, four elevations and one cut per floor is a dozen PNGs per save at roughly 150 KB each. Fine on disk; say if you want fewer by default.
- **Bake-off blinding.** Letters until you reveal, or names from the start.
- **Legacy generate command.** Warn for one release then remove, or remove now.
- **Where parts live long-term.** In the plugin jar (versioned with the compiler) or in the workspace (editable without a build). Proposal is both, jar wins on name clash.
